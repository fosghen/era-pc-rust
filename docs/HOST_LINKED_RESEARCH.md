# Связанный запуск EXE и DLL — 19.10.2026

Продолжение [модели импортов и дескрипторов](REFERENCE_IAT_RESEARCH.md),
исходный коммит `784105d`. Это лабораторная x86-эмуляция, не нативный запуск
ЭРА и не подтверждённый обход лицензирования.

## Последняя подтверждённая точка

Parent остаётся на ResumeThread без его исполнения. Отдельный worker-entry
probe с явным timestamp-сценарием и одним заданным GetTickCount дошёл до
WaitForMultipleObjects после 763 083 инструкций. Ожидание ещё не исполнялось;
связи с устройством/USB не установлено. Подробности и ограничения — в конце
этого хронологического журнала. Рабочего обхода ключа и успешной лицензии нет.

## Подготовка DLL завершилась возвратом

В локальном `grd_reference_iat_04.json` обе стадии закончились возвратом:

| Стадия | Наблюдаемые инструкции с начала | EAX | ESP |
| --- | ---: | --- | --- |
| DLL_PROCESS_ATTACH | 79 770 249 | 1 | `0x70008010` |
| GrdPrepare(-1) | 192 171 396 | 0 | `0x70008008` |

Один аргумент GrdPrepare снят по stdcall, исходный SEH восстановлен после
attach. Ноль здесь — наблюдаемое значение регистра, **не интерпретация
лицензионного статуса**. Создан модельный дескриптор текущего потока;
возврат не доказывает присутствия аппаратного ключа. Реальный USB/драйвер
не использовался. Первые 128 байт `.text` не были просто обнулены.

Инструменты этого прогона соответствуют коду коммита `784105d`, но отчёт
получен уже после его контрольной точки и сохранён отдельно. Старый манифест
не переписывается задним числом.

## Следующая стадия получает параметры от EXE

Новая опция `--host-after-attach /path/to/program.exe` несовместима с
`--after-attach-export` и требует `--dll-attach`. Сначала выполняется
настоящая точка входа выбранной DLL с аргументами attach, затем точка входа
явно выбранного x86 EXE в той же эмулируемой памяти и состоянии потока.
Неуспешный attach, нарушенный стек или невосстановленная SEH запрещают переход.

Импорты EXE с точным именем предоставленной DLL направляются к её существующим
экспортам. Инструмент не возвращает результат вместо них: код DLL выполняется
с аргументами и адресом возврата, которые сформировал EXE. Неизвестные или
перенаправленные экспорты остаются точками остановки. Другие гостевые DLL
автоматически не загружаются и не исполняются.

Оба входных образа проверяются на пересечения с памятью стенда и справочными
модулями. Регистрируются границы стадий, до 256 перенаправлений импортов в
гостевые экспорты,
записи в секции DLL/EXE, наблюдения и хеши проверяемых диапазонов. Виртуальная
защита памяти разрешена только в явно заданных входных образах; справочные
модули остаются read-only. Хеши обоих оригиналов проверяются после завершения.
Байты сторонних образов и дампы памяти не выгружаются в отчёт.

Лимиты инструкций/времени общие. У каждого образа — не более 256 MiB;
начальные разрешения его страниц RWX остаются ограничением стенда. Нет
автоматической загрузки зависимостей, Windows loader lock, PEB, TLS callbacks
зависимостей или полноценного CRT/Windows-процесса. Командная строка,
окружение, часы и идентификаторы всё ещё взяты из явного синтетического
профиля. Поэтому реальные аргументы, сформированные кодом EXE в этой модели,
не равнозначны наблюдению неизменённого нативного процесса Windows.

Синтетические тесты проверяют передачу аргументов, настоящий результат
гостевой функции, общую память после attach, обе стороны stdcall-стека,
наблюдения/записи в EXE, неизменность файлов, пересечения образов и остановку
неизвестного экспорта. На этапе добавления связанного запуска прошёл 81
тест Python; сторонние EXE/DLL этим тестам не нужны.

## Первый связанный прогон расчётного блока

В `perv_linked_01.json` DLL attach вернул 1 на 79 770 249-й инструкции,
затем EXE вызвал настоящий GrdPrepare(-1) на 110 897 552-й. Он возвратился
в EXE; следующий вызов GrdPrepare(1) вернул адрес внутреннего переходника
GetModuleHandleA. Остановка на 228 685 646-й инструкции произошла перед
`api-ms-win-core-libraryloader-l1-2-0.dll!GetModuleHandleA`. Аргумент на стеке
содержит имя `KERNEL32.DLL`. Наблюдатель InitProtApp ещё не сработал.

Исправление первоначальной интерпретации: соседние слова стека содержали
`GRDVKC32.DLL`, но не были строкой по указателю аргумента. Поле
`module_name_argument` исходного отчёта `_01` содержит именно `KERNEL32.DLL`.
Описание в историческом манифесте `...-host.json` отражает прежнюю ошибочную
интерпретацию; сам отчёт и его хеш не менялись.

В служебной `.idata` расчётного EXE наблюдались 46 052 записи; изменений
его `.text` до этой точки не зарегистрировано. Полная распаковка расчётных
функций и численная эквивалентность ЭРА не доказаны. Оригиналы EXE и DLL
прошли проверку неизменности.

После этого добавлен явный реестр двух уже отображённых входных образов:
DLL доступна по собственному имени, EXE — по имени и через GetModuleHandle(NULL).
GetProcAddress возвращает действительные экспортные адреса этих образов,
которые затем исполняются как гостевой код, а не как успешный ответ-заглушка.
Динамическое разрешение записывается в журнал resolver; журнал перенаправлений
IAT не претендует на перечисление всех прямых/косвенных вызовов.
Непредоставленные модули и неизвестные экспорты по-прежнему останавливают трассу.

Для GetModuleHandleA/GetProcAddress поддержано только точное дополнительное
имя контракта `api-ms-win-core-libraryloader-l1-2-0.dll`. Принадлежность
подтверждается официальными метаданными
[GetModuleHandleA](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/libloaderapi/nf-libloaderapi-getmodulehandlea.md) и
[GetProcAddress](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/libloaderapi/nf-libloaderapi-getprocaddress.md).
Тесты проверяют поиск DLL, NULL-имя EXE и выполнение результата GetProcAddress
без справочных системных DLL. Это расширение ещё требует отдельного длинного
прогона; в `_01` оно не применялось.

В `_02` на неизменном коде `7d9920f` зарегистрированы успешные в рамках модели
запросы KERNEL32.DLL, USER32.DLL и GRDVKC32.DLL. Затем расчётный EXE дошёл до
`api-ms-win-core-memory-l1-1-0.dll!VirtualAlloc(NULL, 0x421c, MEM_COMMIT, PAGE_READWRITE)`
на 232 339 096-й инструкции. Это запрос 16 924 байт, а не обращение к ключу.
Начальная подготовка возвращается в EXE, но InitProtApp ещё не наблюдался.

## Ограниченная модель виртуальной памяти

Следующая версия поддерживает новые выделения по NULL-адресу с MEM_COMMIT
или MEM_COMMIT|MEM_RESERVE. Размер округляется до 4096, адрес выбирается
с шагом 65536 внутри явно зарезервированной области модели размером 64 MiB.
Страницы действительно нулевые и имеют заданные разрешения Unicorn, включая
запрет исполнения для PAGE_READWRITE. MEM_RELEASE снимает отображение целого
живого блока; двойное освобождение и неподдержанные операции останавливаются.
Переиспользование, decommit, reserve-only и запрос конкретного адреса не
реализованы. Лимиты модели не выдаются за отказ Windows из-за нехватки памяти.

Вариант NULL + MEM_COMMIT без MEM_RESERVE — явно выбранное поведение
совместимости Windows, описанное Microsoft, а не универсальное обещание
для любого ненулевого адреса.
[Описание поведения](https://devblogs.microsoft.com/oldnewthing/20151008-00/?p=91411),
[VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc).
VirtualProtect/FlushInstructionCache могут работать также с живыми блоками
этой модели; справочные DLL всё ещё не меняются.

Тесты проверяют нули, округление, выравнивание, защиту от исполнения,
переход RW→RX, настоящее снятие отображения, время жизни и отказ без частичной
выдачи памяти при неверных параметрах. Всего проходит 85 синтетических тестов.
Файлы Windows, процессы, устройства и аппаратные ответы эта модель не создаёт.

Первый запуск этой версии был отклонён до исполнения: первоначально выбранный
диапазон арены пересекался с предпочтительной базой справочной comdlg32.dll
`0x52080000`. Проверка пересечений сработала штатно, отчёт трассы `_03` ещё не
был создан. Арена перенесена в проверенный для данного набора модулей диапазон
`0x56000000..0x5a000000`; добавлен отдельный синтетический регрессионный тест
этого расположения и сохранён отказ при настоящем пересечении. Всего 86 тестов.

## Копирование DLL и представление критической секции

На коде `e5239c4` прогон `_03` исполнил 256 078 777 инструкций и остановился
на чтении четырёх байт `0x1036a93c` из гостевой критической секции. Выделены
два блока: 20 480 байт по `0x56000000` и `0x6b3000` байт по `0x56010000`.
Второй размер совпадает с SizeOfImage DLL. В точке остановки EAX указывает
на исходный адрес, EDX — на `0x5637a93c`; разница равна сдвигу базы копии.
Последовательность адресов инструкций и дисковый код с `0x0d2563d6`
согласуются с циклом копирования по четыре байта. Дисковый код здесь не
выдаётся за снятый образ исполняемой памяти. Это ограничение модели Windows,
а не установленная проверка наличия ключа.

С разрешения пользователя выполнен собственный скрипт
`tools/probe_critical_section.ps1` в 32-битном PowerShell Windows. Он создаёт
только свои объекты через API синхронизации, не загружает ЭРА, не обращается
к устройствам/сети/реестру. Первую попытку остановила политика PowerShell;
повтор разрешён с исключением только для процесса, без изменения системной
политики. Add-Type использует временные файлы компилятора Windows.

На ntdll `10.0.19041.4842`, 12 логических процессорах, измерены варианты
InitializeCriticalSection и InitializeCriticalSectionAndSpinCount со spin
0/4000, включая повторный вход, два выхода и удаление. Сохраняются только
значения полей и классификации указателей; нативные адреса/идентификаторы
в модель не переносятся. При свободном объекте LockCount=-1, при захваченном
без конкуренции -2; RecursionCount=0/1/2, OwningThread — ноль/текущий поток,
DebugInfo=-1, LockSemaphore=0. SpinCount для запроса 0 наблюдался как
`0x020007d0`, для 4000 — 4000. Это **измерение конкретной реализации**, не
универсальный контракт Windows; официальное
[описание полей](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/displaying-a-critical-section)
также различает версии системы.

Опция `--critical-section-layout win10-x86-19041` включает ограниченный
профиль этих 24 байт для одного потока. По умолчанию объект остаётся opaque
и прямой доступ останавливается. С профилем чтение/копирование разрешено,
API обновляют поля, но запись гостевого кода, неизвестный spin, конкуренция
потоков и использование копии как зарегистрированного объекта не реализованы.
Владелец — синтетический TID стенда. Профиль не обрабатывает лицензирование.
Всего 93 синтетических теста; нативный тест не запускается в CI.

Дополнительный аудит нашёл ограничение диапазонных hooks Unicorn: проверялся
начальный адрес доступа, поэтому четырёхбайтная запись за два байта до объекта
не останавливалась, хотя пересекала его. Исправление проверяет пересечение
полного диапазона глобальным наблюдателем памяти. Чтение также проверяется
в непрозрачном режиме; в измеренном профиле оно разрешено. Регрессии покрывают
обе границы, соседние непересекающиеся записи и удалённые объекты; всего 95
тестов. Исторические прогоны до исправления не считаются проверенными на этот
краевой случай. Прогон `_04` был запущен с зафиксированного кода `4bd2a62`
до этого исправления и требует отдельного повторения на исправленном коде.

## Следующая граница: представление системного времени

В `_04` на коде `4bd2a62` копирование прошло прежнюю остановку, затем
MEM_RELEASE освободил временный блок `0x56010000`. Остановка на
281 280 045-й инструкции — `api-ms-win-core-sysinfo-l1-1-0.dll!GetSystemTime`,
адрес возврата `0x0d334ff5`, выходной буфер `0x70007f60`. Наблюдатель
InitProtApp ещё не сработал; расчётное ядро не запущено. Это промежуточное
наблюдение до повторной проверки исправленным наблюдателем границ.

Повтор `_05` на коде `88fbff0` с глобальной проверкой пересечений подтвердил
ту же границу: 288 052 740 инструкций, 407,3846 с. Совпали имя API,
девять наблюдаемых слов стека, все итоговые регистры, количества записей в
секции и все три проверяемых диапазона памяти. Хеши пяти инструментов
сверены с Git-кодом соответствующих коммитов, оба входных файла неизменны.
Разное число инструкций не скрывается: RDTSC пока не фиксирован, полная
детерминированность стенда не установлена.

GetSystemTime добавлен как другое представление **той же** заранее заданной
FILETIME тестового профиля (2024-01-01 00:00:00 UTC). Дата не подбиралась по
результатам защиты и не берётся с компьютера. Формируются 8 WORD структуры
SYSTEMTIME, воскресенье=0, доли миллисекунды отбрасываются целочисленно;
VOID-функция не получает придуманного кода успеха в EAX. Не реализованы
локальный часовой пояс и течение времени. Ограничение календаря этой модели
1601..9999 уже документированного диапазона Windows. Добавлены проверки
високосного дня, границ, буфера и stdcall; всего 98 синтетических тестов.
Контракты:
[GetSystemTime](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemtime),
[SYSTEMTIME](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-systemtime),
[точное имя API-set](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/sysinfoapi/nf-sysinfoapi-getsystemtime.md).

В `_06` на коде `fa075f8` GetSystemTime записал эти 16 байт в буфер, затем
загрузчик продолжил исполнение до лимита 300 000 000 инструкций (419,0851 с).
Остановка в `0x0d35e7c0`, записей в добавленную `.idata` EXE — 111 414.
InitProtApp всё ещё не наблюдался; распаковка основного расчётного кода не
подтверждена. Для следующего опыта явный верхний предел увеличен до
600 000 000 инструкций / 900 с, но значения по умолчанию остались
20 000 000 / 45 с. Ограничения теперь одинаково проверяются CLI и библиотечным
входом; прогресс показывает и прошедшее время. Всего 99 синтетических тестов.

## Первый наблюдаемый вход в InitProtApp

Прогон `_07` на коде `773e6d2` впервые зарегистрировал вход в настоящий
InitProtApp (`0x100095b0`) на 313 652 334-й инструкции. Адрес возврата
`0x0d335797`; два аргумента, сформированные EXE: `0x0d25a97d` и 0. Соседнее
слово стека `0x56000000` не является третьим аргументом. Эти значения не
подбирались экспериментатором. Отдельный наблюдатель возврата пока не задан,
поэтому факт входа не выдаётся за успешное завершение или статус лицензии.

После 600 000 000 инструкций (743,0251 с) стенд остановился по лимиту в
`0x0d255a7f`. Записей в служебную `.idata` EXE — 454 666; в `.text` расчётного
EXE записей по-прежнему не зарегистрировано. Последний обработанный системный
API — GetSystemTime. Оба входных образа неизменны; численного расчёта,
обращения к физическому ключу и успешной проверки лицензии не наблюдалось.

Следующая задача — измерить и сократить накладные расходы наблюдателя, прежде
чем увеличивать бюджет очередного опыта. На собственном коротком цикле из
400 001 инструкции bare Unicorn занял около 0,0028 с, а добавление только
счётчика через Python callback — около 0,231 с. Это одиночный синтетический
микротест, **не** измерение ускорения полной трассы или расчётов ЭРА.

Хеши инструментов и локальных отчётов зафиксированы в

## Проверка сохранности контрольных точек

[Отдельный манифест критических секций](research-checkpoint-2026-10-19-critical-sections.json)
сохраняет этап до повторов `_05`/`_06`, включая обезличенные измерения
собственного Windows-теста. Старые манифесты не обновляются под новые файлы.
Локальный архив этой точки содержит 15 файлов: только наши инструменты,
документацию, манифест и метаданные наблюдений, без сторонних бинарных файлов.

Проверка из каталога `era-rust`:

```sh
python tools/verify_checkpoint.py docs/research-checkpoint-2026-10-19-critical-sections.json --root .. --archive ../reverse_engineering/checkpoint-20261019-critical-sections.tar.gz
```

Без `--archive` сверяются текущие файлы рабочего каталога. Их несовпадение со
старой точкой после дальнейших коммитов ожидаемо; для исторического состояния
нужен соответствующий архив. Команда никогда не распаковывает архив и ничего
не изменяет. Проверяются точный набор файлов, включённый манифест и SHA-256;
повторные имена, ссылки в архиве и выход путей за корень отвергаются. Лимиты:
1024 записи, 128 MiB на файл, 512 MiB на набор, 4 MiB на манифест.
Коды выхода: 0 — совпадение, 1 — несовпадение/отсутствие, 2 — некорректный
формат или ошибка чтения. Хеши не доказывают подлинности самого манифеста,
правильности интерпретации трассы или численной эквивалентности ЭРА.
С учётом проверок этого инструмента проходит 107 синтетических тестов.

## Нативный наблюдатель на Rust

Добавлен явный режим `--observer rust`: счётчик начала инструкций и кольцевая
история последних 24 адресов выполняются в нашем Rust callback без перехода
в Python на каждой инструкции. Гостевые PE по-прежнему исполняются только
в Unicorn. Редкие контрольные адреса, импортные маркеры и вся область
справочных модулей передаются прежнему Python-обработчику. Обработка памяти,
API и ограничения эксперимента не отключаются ради скорости.

Python остаётся режимом по умолчанию и эталоном для сравнения. Новая опция
сейчас поддерживает **исследовательский Linux x86_64 / WSL** с Unicorn 2.1.4
и установленным `rustc`. Это не ограничение платформы будущего Windows CLI.
Неподдержанный хост, версия или отсутствие компилятора вызывают ошибку,
а не незаметный переход к другому режиму.

Адаптер компилирует только наш `tools/trace_observer.rs` во временном каталоге,
проверяет ABI и удерживает callback до удаления hook. Исключения из callback
останавливают исполнение и передаются вызывающему коду. Счётчик и история
синхронизируются перед диагностикой ошибок, записью событий наблюдения и
после каждого блока исполнения. В отчёт включаются SHA-256 исходника,
адаптера, собранной библиотеки, версия и параметры компилятора. Исходный
код снимка фиксируется перед компиляцией. Библиотека не публикуется.

Из каталога `era-rust`, при наличии `rustc` в PATH (или переменной `RUSTC`
с полным путём), к прежней команде трассировки добавляется `--observer rust`.
Самостоятельный воспроизводимый тест скорости без файлов ЭРА:

```sh
python tools/benchmark_observer.py --instructions 1000000 --repeats 3 --report /new/path/observer-benchmark.json
```

Локальное измерение `observer_benchmark_01.json`, медианы трёх прогонов:

| Собственный синтетический цикл, 1 млн инструкций | Python | Rust | Ускорение |
| --- | ---: | ---: | ---: |
| Арифметика без записей в память | 0,6531 с | 0,0161 с | 40,57× |
| Частые записи в стек | 1,2662 с | 0,5509 с | 2,30× |

Подготовка Rust-библиотеки в этом процессе заняла около 0,078 с и не входит
во время исполнения. Полные смысловые отчёты совпадают; из сравнения
исключаются только время и метаданные выбранного наблюдателя.

**Проверка на реальном входном файле:** прежний связанный сценарий DLL + EXE,
десять справочных DLL, NLS, модель критических секций и прежние наблюдения,
лимит 20 000 000 инструкций / 120 с. `perv_observer_python_20m_01.json`:
30,7878 с; `perv_observer_rust_20m_01.json`: 14,3491 с — **2,15×**.
Совпадают все поля отчётов, кроме `elapsed_seconds` и `instruction_observer`,
включая регистры, API, записи, последние инструкции, хеши наблюдаемых областей
и неизменность входных файлов. Это одна пара измерений, а не статистический
прогноз для любых участков программы. Во время Python-прогона кратко
выполнялись также тесты CLI; измерение не проводилось на выделенном CPU.

600-миллионный сценарий с Rust на этом этапе **не повторён**; ускорение
предыдущего 12-минутного прогона не измерено. Не фиксируемый стендом RDTSC
может влиять на последующие пути; совпадение этого префикса не доказывает
детерминированности всей программы. Поддержка памяти в Python остаётся
существенной затратой — её цена видна даже на синтетическом цикле записей.

Проверки: 167 тестов инструментов, включая дифференциальные сценарии
возврата, DLL attach, связанных вызовов EXE/DLL, API, самомодификации,
неизвестной памяти, прерываний, переполнения журнала, точных лимитов,
нескольких блоков исполнения и исключения callback. Все 59 тестов
расчётного Rust-проекта с локальным корпусом также прошли; его алгоритмы
этим изменением не менялись. В CI добавлена сборка наблюдателя и эти тесты
только на собственных синтетических PE, без сторонних образов и без
публикации исполняемых файлов.

## Ускорение фильтрации памяти на Rust

Следующий этап переносит в Rust отбор событий памяти, а не меняет их смысл.
`--observer rust` теперь включает оба ускорения. Для отдельной проверки
старого смешанного режима есть `--observer rust --memory-observer python`.
Python остаётся эталонным режимом по умолчанию. Режим Rust для памяти требует
Rust-наблюдатель инструкций; неподдержанные сочетания отклоняются.

Профилирование на префиксе из 2 млн инструкций выявило по **525 363** вызова
Python-функций `written` и `guard_critical_section_access`. После переноса:
`written` вызывается **5 206** раз, а guard — 0 раз: ни одно CPU-обращение
этого префикса не пересекает защищённые объекты. Проверка их пересечения
всё равно выполняется, но нативно. Осталось 188 Python-вызовов обработчика
памяти TIB/TEB — их оставили без изменений. Под профилировщиком скорость
не оценивается: здесь используются именно счётчики вызовов.

Новый нативный hook считает все обращения и передачи в Python. Для образов
сохранён прежний отбор **по началу записи**, для критических секций —
**по пересечению полного диапазона доступа**, включая запись до начала
объекта. Список живых объектов синхронно обновляется при создании/удалении.
Смежные интервалы объединяются только для фильтрации; модель объектов,
ограничения, обработка ошибок, порядок hooks и журналы остаются прежними.
Релевантный доступ передаётся исходному Python-обработчику. Нативный фильтр
сам не выдаёт ответы API и не модифицирует гостевую память.

### Три режима на одинаковой реальной трассе

Все три отчёта `perv_memory_*_20m_01.json` получены одной версией инструментов,
с одинаковыми входными файлами, моделями, наблюдениями и лимитами:
20 млн инструкций / 120 с.

| Режим | Время исполнения |
| --- | ---: |
| Python | 33,7328 с |
| Rust для инструкций, Python для памяти | 14,0406 с |
| Rust для инструкций и фильтрации памяти | **3,4299 с** |

Совпадают **все поля** трёх отчётов, кроме `elapsed_seconds` и
`instruction_observer`. Ускорение относительно Python — **9,83×**,
относительно предыдущего смешанного режима — **4,09×**. Один комплект
последовательных прогонов на общем рабочем хосте, без закрепления CPU;
не статистическая гарантия. Время подготовки PE/компиляции, как и ранее,
не включено в `elapsed_seconds`.

В нативном режиме каждый из двух глобальных фильтров обработал 5 243 422
события. В Python передано только 44 853 записи в образы; в guard — ни одного
события. Таким образом, из 10 486 844 потенциальных Python-вызовов этих
обработчиков отфильтровано около 99,57%, без отключения защитных проверок.

Синтетический benchmark теперь сравнивает все три режима, чередуя порядок
в трёх повторах. На цикле частых записей в стек медианы: Python 1,3365 с,
Rust-инструкции 0,5852 с, оба Rust-фильтра 0,0569 с — **23,49×** относительно
Python и **10,28×** относительно первого переноса. Арифметический цикл без
памяти существенно не выиграл от второго этапа, что ожидаемо.

### Длинный прогон после оптимизации

`perv_memory_rust_600m_01.json`: **600 000 000 инструкций за 48,5362 с**, остановка
по лимиту, а не по таймауту или отключённому наблюдению. Исторический `_07`
с тем же бюджетом занял 743,0251 с — отношение времён **15,31×**. Это сравнение
одинакового бюджета, **не доказательство одинакового пути исполнения**:
RDTSC не фиксирован, конечные регистры и индексы промежуточных событий
различаются. Строгое совпадение проверено на 20-миллионном префиксе выше.
В начале длинного прогона кратко шли также тесты расчётного CLI; измерение
не проводилось на выделенном CPU.

DLL attach вернул 1 на 79 543 321-й инструкции. InitProtApp снова наблюдался
на 322 096 537-й инструкции с теми же двумя аргументами EXE: `0x0d25a97d`, 0;
адрес возврата `0x0d335797`. Сам возврат этой функции не наблюдался отдельной
точкой. Записей в `.text` расчётного EXE по-прежнему нет; в `.idata` — 449 725.
Конечные хеши всех трёх наблюдаемых диапазонов совпадают с `_07`. Входные EXE,
DLL, справочные модули и NLS не изменены. Расчёт рассеивания и успешная
проверка лицензии этим прогоном не подтверждены.

Два глобальных фильтра каждый получили 69 054 872 события; в Python передано
607 119 записей в образы и 0 пересечений критических секций. В отчёте сохранены
счётчики, ABI 2 и происхождение собранного нативного кода. Бинарные файлы
наблюдателя/ЭРА и дампы памяти не публикуются.

Пройдено **216 тестов инструментов** и прежние **59 тестов расчётного проекта**.
Добавлены проверки пересечений/смежности, динамических пустых интервалов,
атомарного отклонения неверного обновления, 128 живых объектов, удаления и
повторного создания, порядка защитного hook и журнала записи, исключений
нативного callback и режима сравнения без фильтра памяти. Весь набор тестов
StartupModel также повторён с нативным guard. Результаты фиксируются в
[отдельной контрольной точке](research-checkpoint-2026-10-19-memory-observer.json).

## Возврат InitProtApp и записи во всю дисковую секцию `.text`

Исследование продолжается отдельно от расчётного CLI. Добавлена точка
наблюдения адреса возврата `0x0d335797`; события теперь сохраняют ESP.
`perv_init_return_600m_01.json` первым зафиксировал этот адрес с EAX=0,
но ещё без ESP. Его исходник соответствует предыдущей контрольной точке
memory-observer, а не более поздней версии с новым полем.

`perv_after_init_2b_02.json`: **2 000 000 000 инструкций за 189,4428 с**,
остановка по лимиту. InitProtApp наблюдался на инструкции 327 990 569,
ESP=`0x70007f78`, аргументы `0x0d25a97d`, 0. Адрес возврата достигнут на
350 173 051, ESP=`0x70007f84`, EAX=0. Разница ESP=12 соответствует удалению
адреса возврата и двух 32-битных аргументов. **Значение EAX=0 не трактуется
как подтверждение лицензии.**

После этого модель зарегистрировала VirtualProtect для адреса `0x401000`,
размера `0x50c000`. В `.text` EXE впервые наблюдаются **6 614 400** CPU-записей
в диапазоне `[0x401000, 0x90ce00)`: это 5 291 520 байт, ровно SizeOfRawData
секции. Все 128 байт небольшого наблюдаемого префикса изменились; сохранены
только хеши, число изменений и адреса записей, не содержимое кода.

По дисковому коду функция `0x0d255738..0x0d25585d` обрабатывает блоки по
16 байт: четыре DWORD-записи результата преобразования и 16 побайтовых
XOR-записей. Равенство `5 291 520 / 16 * 20 = 6 614 400` вместе с диапазоном
согласуется с одним полным проходом по дисковому содержимому `.text`.
Это **интерпретация совокупности наблюдений**, а не доказательство корректной
расшифровки или работоспособности получившегося кода. Ещё 512 байт VirtualSize
не входят в этот диапазон.

Конечный EIP `0x0d255a51` находится в блочном арифметическом ядре с 64 раундами,
восемью словами состояния и вращениями 6/11/25, 2/13/22; это не наблюдаемый
цикл ожидания USB. Дальнейшее назначение результата требует вызывающего
контекста. Статический разбор изменяемых участков `.idata` после InitProtApp
по исходным дисковым байтам не даёт надёжного графа выполнения.

Исходные EXE/DLL, справочные модули и NLS не изменены. Не зафиксированы
обращение к аппаратному ключу, успешное лицензирование или запуск расчёта.
Пройдено 216 тестов инструментов. Исторические исходники и два новых отчёта
сохранены в локальном архиве; 13 записей, включая манифест, проверены без
распаковки по [контрольной точке host-text](research-checkpoint-2026-10-19-host-text.json).
Архив, отчёты и сторонние файлы не предназначены для публичного репозитория.

### Диагностика будущей границы файлового/аппаратного API

Для следующего эксперимента верхняя граница инструкций поднята до 4 млрд;
предел времени остаётся 900 с, значения по умолчанию — 20 млн / 45 с.
Это не изменение ответа защиты или модели Windows. Счётчик нативного
наблюдателя 64-битный; исполнение по-прежнему разбито на ограниченные порции.

Остановка на неизвестном `kernel32.dll`/`kernelbase.dll!CreateFileA/W`
теперь сохраняет семь именованных аргументов и ограниченное имя объекта
(до 260 единиц вместе с терминатором). Для A декодируется только строгий
ASCII: не-ASCII не угадывается, ошибка сохраняется отдельно. Для W — UTF-16LE.
На `DeviceIoControl` сохраняются восемь аргументов, но содержимое входных
и выходных буферов не читается. Ошибки чтения не меняют причину остановки
`external_import`; никаких файлов/устройств стенд не открывает, дескрипторов
или ответов лицензирования не создаёт. Другие имена API остаются обычными
точками остановки с исходными словами стека.

Эта диагностика проверена только на собственных синтетических PE, включая
неверные указатели, NULL, границы длины, ошибки кодировок и нечитаемый стек.
Все **228 тестов инструментов** прошли; новые сценарии включены также в
дифференциальное сравнение Python/Rust. Само наличие декодера не означает,
что оригинал уже обратился к устройству.

## Выход из обработки секций и следующая зависимость Windows

`perv_after_init_4b_02.json` остановился не по лимиту, а на неизвестном импорте:
**3 407 867 979 инструкций за 238,9212 с**. Новые точки наблюдения на входе
`0x0d255738` и возврате `0x0d25585d` подтвердили реальные границы обработки
целого буфера. Аргументы и ESP на входе/возврате согласованы.

| Буфер | Длина | Вход, индекс инструкции | Возврат, индекс инструкции |
| --- | ---: | ---: | ---: |
| `.text`, `0x401000` | 5 291 520 | 1 291 304 655 | 1 950 098 905 |
| `.itext`, `0x90d000` | 3 584 | 3 404 390 068 | 3 404 836 286 |

Зафиксированы 6 614 400 и 4 480 записей соответственно. Затем обработаны
служебные буферы по адресам `0x0d23b000` (12 800 байт), `0x0d23e200`
(1 600 байт); вызов с нулевой длиной также вернулся. Исходные файлы неизменны.

Следующий вызов — `api-ms-win-core-libraryloader-l1-2-0.dll!GetModuleHandleA`,
адрес возврата `0x0d32aeac`, имя аргумента **`oleaut32.dll`**. Модель честно
остановилась: эта DLL не была явно отображена. Это установленная зависимость
среды, не обнаруженный запрос ключу. Её локальный SysWOW64-образ имеет
предпочтительную базу `0x10000000`, совпадающую с базой `grdvkc32.dll`;
простое добавление файла без поддержки перемещения не решает конфликт.

Предварительный `_4b_01` остановился раньше, на 315 654 512 инструкциях:
частые наблюдения хеш-обёртки исчерпали журнал из 256 событий. Это лимит
диагностики, не ветвь отказа защиты. Во втором опыте эти частые наблюдения
убраны; остальные правила исполнения сохранены. Оба опыта используют
исходник `b33dd59a…`, отдельно сохранённый до добавления декодера файловых API.
RDTSC по-прежнему не фиксирован, поэтому индексы разных опытов не равнозначны
детерминированному повтору одного пути.

### Независимая проверка найденной хеш-функции

Локальный `probe_sha256_wrapper.py` вызвал оригинальную дисковую функцию
`0x0d2562c8` в отдельной ограниченной памяти Unicorn. Отображена только
содержащая её секция; стек, входы и выход собственные. Восемь входов:
пустой, ASCII `abc`, а также длины 55, 56, 63, 64, 65, 1000 по формуле
`bytes((i*37+11)&255 for i in range(n))`. Все 32-байтовые результаты совпали
с `hashlib.sha256`, все вызовы вернулись с ожидаемым cdecl-стеком. Лимит
каждого случая — 2 млн инструкций / 10 с; фактически 15 604–280 884 инструкции.
Ни импортов, ни Windows API, ни патчей исходного кода не потребовалось.

Это экспериментальное подтверждение SHA-256 на выбранных входах, а не полное
доказательство для любых входов и не установление роли хеша в лицензировании.
Отчёт `sha256_wrapper_probe_01.json` сохраняет формулу, digest, время,
счётчики, версии и SHA-256 входного EXE/инструмента. Локальный архив
проверен по [контрольной точке section-return](research-checkpoint-2026-10-19-section-return.json)
(14 файлов с манифестом); vendor-байтов в нём нет.

### Явное размещение справочных PE при конфликте адресов

Добавлена опция `--module-base NAME=ADDRESS`, действующая только на явно
переданные `--module` справочные образы. Без неё сохраняется предпочтительная
база; размещение EXE и защитной DLL не меняется. Новые адреса не выбираются
автоматически. Пересечения, неизвестные имена и повторные override отклоняются.

Поддержаны только PE32/x86 релокации ABSOLUTE (пропуск) и HIGHLOW (прибавление
разности баз к 32-битному полю), согласно
[спецификации Microsoft PE/COFF](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#the-reloc-section-image-only).
Таблица должна полностью лежать в однозначно определённых дисковых данных;
проверяются размеры, выравнивания, типы, границы и пересечения исправляемых
полей. Все исправления проверяются до изменения частного образа. Отсутствующая,
обрезанная или неподдержанная таблица не считается успешно обработанной.
Заголовочный ImageBase не подменяется новым адресом вручную.

Экспорты и IAT-слоты привязаны к фактической базе; отчёт сохраняет также
предпочтительную базу, знаковую разность и число HIGHLOW-исправлений.
Справочные страницы остаются read-only, попытка исполнить их код останавливается
до первой инструкции. Никакой загрузки драйвера, DllMain или ответа ключа нет.

Предварительная проверка всех 16 явно выбранных справочных образов прошла:
`oleaut32.dll` размещена на `0x61000000` (12 006 исправлений), `wininet.dll` —
на `0x61200000` (36 770). У второй предпочтительный диапазон пересекает
`shlwapi.dll`; остальные 14 образов оставлены на предпочтительных базах.

в процессе исполнения. Всего 7 366 обычных IAT-маркеров; все входы неизменны.
Это проверка размещения без выполнения API, не результат длинной трассы.

Пройдено **245 тестов инструментов**: в том числе знаковые разности и
переполнение по модулю 32 бит, испорченные таблицы, недопустимые базы,

### Ограниченная модель API-set v6

Опция `--api-set-schema PATH` разрешает использовать только явно переданный
PE-файл со схемой. Контракт API-set не обязан соответствовать файлу DLL:
Windows связывает его с host-библиотекой через системную схему, как описано в
[API set loader operation](https://learn.microsoft.com/en-us/windows/win32/apiindex/api-set-loader-operation).
Самостоятельно выбирать host по похожему имени модель не пытается.

Поддержана проверенная локально форма namespace v6: хеш префикса до последнего
дефиса, точное сравнение префикса при коллизиях, ровно одно значение host без
alias. Источник ограничен 16 MiB, namespace — 16 384 записями/значениями,
строки — 260 символами; проверяются UTF-16/ASCII, границы, хеши, сортировка и
перестановка индексов. Неподдержанные версии/формы, namespace flags, flags
выбранного значения, неоднозначность, selector-записи и пустой host дают
явную ошибку. Для flags записи принимаются только наблюдавшиеся 0/1, они
явно отражены в результате разрешения. Полная доступность ревизии API не проверяется.

Разрешение допускается только в уже отображённый справочный host. Сначала
проверяется явно зарегистрированное имя модуля; схема используется для
отсутствующего `api-`/`ext-` имени. Ни файлового поиска, ни загрузки новых DLL,
ни вызова их инициализаторов/экспортов нет. GetModuleHandle и экспортные
forwarder-цепочки используют одну модель; адрес host остаётся точкой остановки.
Отчёт сохраняет хеши файла/namespace/исходника модели и использованные
соответствия. Исходная схема повторно проверяется на неизменность.

Файловая схема **не заявляется эквивалентной live-схеме Windows-процесса**:
расширения, композиция и importer-specific selectors не реализованы.
Новый статический preflight с 17 reference-модулями, включая `combase.dll`
на `0x61800000` (71 325 HIGHLOW-исправлений), разрешил все 318 обычных системных
импортов двух входных образов. Это проверка таблиц, не выполнение этих функций.

Пройдено **264 теста инструментов**, включая 15 тестов схемы и связанные
синтетические сценарии поиска модуля/forwarder в Python и Rust. Длинный
прогон с этой моделью фиксируется отдельно от предварительной проверки.

Ревью обнаружило, что первая версия не отклоняла неизвестные entry flags.
Добавлена проверка и регрессия. Начатый до этого длинный опыт использует
исходник схемы `7440581c…`, сохранённый отдельно; в конкретной локальной
схеме все 891 записи имеют только flags 0/1, COM — 1. Поэтому найденный
пробел не устанавливает ошибку разрешения данного контракта, но ограничение
важно для иных входов. Старый отчёт нельзя приписывать исправленному исходнику.

### Явная fixture имени компьютера

Для следующего опыта добавлен необязательный `--computer-name ERA-RE-LAB`
вместе с `--startup-model`. Без этого параметра GetComputerNameA/W, как и
раньше, останавливают трассу. Имя не читается из ОС: это отмеченная в отчёте
синтетическая предпосылка, не ответ ключа и не результат проверки лицензии.

Модель принимает 1–15 ASCII-символов `[A-Z0-9-]`. Размер измеряется в TCHAR:
успех записывает имя с NUL и длину без NUL; недостаточная ёмкость возвращает
0, требуемый размер с NUL и ERROR_BUFFER_OVERFLOW (111). При успехе ранее
заданное last-error сохраняется. Основание контракта —
[GetComputerNameA](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getcomputernamea).

Это ограниченная fixture, не полная эмуляция WinAPI: ёмкость не больше 4096,
буферы валидные и неперекрывающиеся; даже нулевая ёмкость требует доступного
ненулевого указателя. До любых записей проверяются границы, права READ/WRITE
для размера, WRITE для объявленной области вывода и пересечения с opaque
critical sections. Неподдержанный случай останавливается с model_error,
а не подменяется успешным/неуспешным ответом Windows.

**282 теста инструментов проходят**, включая A/W, границы размеров,
невалидные/readonly указатели, отсутствие частичных записей, сохранение
stdcall-стека и Python/Rust parity. Результат реального опыта приводится
отдельно: тесты fixture сами по себе ничего не доказывают о защите ЭРА.

### Использование имени: статический разбор защитной DLL

Дисковый код `0x100345e0..0x10034672` доступен для прямого разбора.
Сразу после GetComputerNameA инструкция `0x10034632` вызывает GetVersion
через IAT `0x1034a24c`, с возвратом `0x10034638`. BOOL имени немедленно
перезаписывается, обновлённая длина не используется. Вход следующего
преобразования — 72 байта (S — ESP после пролога и сохранения ESI/EDI):

| Смещение от S | Байт | Содержимое |
|---|---:|---|
| +0x14 | 8 | RDTSC через `0x100346f0` |
| +0x1c | 8 | QueryPerformanceCounter |
| +0x24 | 4 | GetTickCount |
| +0x28 | 16 | Полный буфер GetComputerNameA |
| +0x38 | 4 | GetVersion |
| +0x3c | 32 | Предыдущее состояние `0x1036add0` |

В `0x1003465c` вызывается wrapper `0x10034e40` с output=`0x1036add0`,
input=`S+0x14`, length=`0x48`; внутри вызывается `0x10035ba0`,
последовательность init/update/final. В init `0x10035810` присутствуют
восемь начальных слов SHA-256; раундовые константы также соответствуют
SHA-256. Это статическая идентификация; отдельный динамический тест
именно DLL-wrapper фиксируется отдельно от прежнего EXE-wrapper.

Потребители обновляют состояние и возвращают первый DWORD (`0x100346a0`),
копируют 32 байта (`0x100346b0`) либо берут первый DWORD по модулю
argument+1 с отдельным случаем `0xffffffff` (`0x100346d0`). Это с высокой
уверенностью обновление генератора псевдослучайных значений с примесью
окружения. Прямого сопоставления имени с разрешённым значением или
обращения к ключу в этом участке нет.

Существенное ограничение: 16 байт буфера имени предварительно не зануляются
в этой функции; в преобразование включается и остаток после NUL. Остаток
стека и RDTSC могут менять состояние между опытами. Тестовая строка сама
по себе не делает запуск детерминированным и не воспроизводит реальный ПК.

Отдельный ограниченный опыт `dll_sha256_wrapper_probe_01.json` подтвердил
DLL-wrapper на **8/8** собственных входах: empty, ASCII `abc` и последовательности
`bytes((i*37+11)&255 for i in range(n))` длиной 55, 56, 63, 64, 65, 1000.
Все 32-байтовые результаты точно совпали с `hashlib.sha256`.
Wrapper имеет thiscall-контракт: ECX указывает на собственный объект
0x178 байт, стек содержит output/input/length, `ret 12`, EAX возвращает
указатель объекта. Во всех случаях ESP восстановлен до initial+16,
SEH-цепочка восстановлена после двух записей, поля объекта +0x16c/+0x170/+0x174
обнулены. Количество инструкций по случаям: 6830, 6929, 8367, 14564, 14769,
14836, 14876, 127960 (sentinel не считается).

Каждый случай ограничен 2 млн инструкций и 10 секундами. Исходный образ DLL
отображён RX; исполняется только исходная code section, записи разрешены
только в собственные output/object/stack/FS:[0]. Нет патчей, привязки импортов,
ответов API, нативного исполнения или обращения к ключу. DLL и исходник
probe не изменились. SHA-256 own script:
`8434ad8a7cc66976be97cfeb235285e7739afa011f4fc37a5fc597be7c0ae08d`;
report: `93a0356215d200624fd5c0a8cb692e5252801c982ca317ae0b94104fc0ef00e9`.
Это подтверждает вычислительную функцию, не её роль в лицензировании.

### Явная fixture GetVersion

Опция `--get-version-result` вместе с `--startup-model` задаёт packed DWORD
без чтения реальной версии ОС. По умолчанию GetVersion остаётся точкой
остановки. Поддерживается только NT-форма 0..0x7fffffff; bool и прочие типы
не принимаются в библиотечном API. Ответ сохраняется в profile/event,
память и last-error не меняются, снимается только адрес возврата (0 аргументов).

Выбранное для следующего опыта `0x4a61000a` декодируется как 10.0/build19041,
но **не утверждает, что оригинальное приложение получило бы такой ответ**.

См. [контракт Microsoft GetVersion](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getversion).

### Ограниченная модель безымянного события

Startup model поддерживает CreateEventA/W только с NULL security attributes
и NULL name. Ненулевые BOOL трактуются как TRUE. Создаётся исключительно
синтетическая identity с manual-reset/начальным signaled флагами; настоящего
объекта Windows нет. Основание —
[CreateEventA](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createeventa).

Общий с DuplicateHandle лимит — 128 дескрипторов за опыт, без повторного
использования номеров. Дубликат с SAME_ACCESS ссылается на тот же объект;
закрытие последнего дескриптора помечает объект destroyed. Число живых
дескрипторов в отчёте вычисляется по их реестру. Превышение бюджета,
именованный объект или security descriptor останавливают модель, а не
превращаются в придуманную ошибку ОС. Для успешного создания нового
безымянного объекта last-error не определён документацией: модель отмечает
его неизвестным (`None`), не выдумывает 0/ERROR_ALREADY_EXISTS.

SetEvent, ResetEvent, WaitForSingleObject, CreateThread и планирование
не реализованы и остаются остановками. Поддержан только точный наблюдавшийся
API-set `api-ms-win-core-synch-l1-1-0.dll` для CreateEventA/W, не wildcard.
**306 тестов проходят**, включая общую identity, last-close, атомарность
ошибочного DuplicateHandle, смешанный бюджет, ограничения модулей и
Python/Rust parity на синтетическом PE. Результат следующего реального
опыта учитывается отдельно.

### Семь событий и частично исполненный CreateThread

`perv_event_4b_01.json`: **3 507 199 786 инструкций за 243,0066 с**.
Созданы семь синтетических безымянных событий: manual-reset по порядку
TRUE, TRUE, TRUE, FALSE, TRUE, FALSE, FALSE; все nonsignaled и с одним живым
дескриптором. Последний CreateEvent возвращается в `0x1000da78`.

Далее GrdPrepare(0x13) возвращается в `0x1000daa9`; его дисковая ветка
возвращает `0x10001980`. Трасса останавливается на `0x6b8211bb` внутри
справочной kernel32.dll. Это **CreateThread + 11**, а не вход экспорта
(`0x6b8211b0`). Пролог уже соответствует состоянию ESP=`0x70007f68`,
EBP=`0x70007f6c`, EAX=4. На вершине стека находится не адрес возврата,
а копия указателя thread ID. Простое переименование этой остановки в
обычный stdcall CreateThread дало бы неправильные аргументы и стек.

Восстановленный исходный вызов: return=`0x1000daab`, security=NULL,
stack size=0, start=`0x1000f950`, parameter=`0x0d25a97d`, flags=4,
thread ID output=`0x103661d4`. Флаг 4 — CREATE_SUSPENDED: поток не должен
исполняться до ResumeThread; см.
[CreateThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createthread).
Ни поток, ни его дескриптор ещё не созданы даже в модели.

Отдельный `create_thread_frame_probe_01.json` проверил интерпретацию:
5 исходных инструкций reference-пролога восстановили **все 9 регистров и
9 слов стека** остановки; следующие 8 инструкций довели до call@`0x6b8211d1`,
но сам вызов не исполнялся. Аргументы следующего CreateRemoteThreadEx:
`[0xffffffff, 0, 0, 0x1000f950, 0x0d25a97d, 4, 0, 0x103661d4]`.
Таким образом речь идёт о текущем процессе, не о внедрении в другой процесс.

Это отдельный bounded reference-code probe, **не разрешение исполнения
reference DLL в основном трассировщике**. Image RX, IAT неизменна, записи
только в собственный стек, лимиты каждой стадии 100 инструкций / 1 секунда;
нативного Windows-вызова нет. Все входы неизменны. Хвост основной трассы
подтверждает вычисляемый переход через DLL `0x10002cc0..0x10002cd1`, но
место исполнения эквивалента пролога текущий короткий хвост не показывает.

SHA-256 probe source:
`9d2f28eadd87562853362432ed5ebd0badfe8213f24a8be60ce37caf6a1af847`;
probe report: `fd6071ed089986aef500b9096af22381635216610879f3088e4aa8fa331f8c07`.
Обход лицензии и взаимодействие с ключом не установлены.

### Модель только приостановленного потока и нормализация входа

`--suspended-threads` требует `--startup-model`; по умолчанию CreateThread
и CreateRemoteThreadEx остаются остановками. Разрешена только identity
CREATE_SUSPENDED (flags ровно 4), NULL security и stack size=0; RemoteThreadEx
дополнительно требует текущий процесс `0xffffffff` и NULL attributes.
Никакого запуска, стека потока, TLS, DLL_THREAD_ATTACH, планировщика или
нативного объекта ОС нет. Начальный адрес хранится как аргумент, не как
доказанно исполняемый код. ResumeThread/Wait/GetExitCodeThread не реализованы.

Синтетический ID начинается с 4098. Необязательный thread-ID DWORD пишется
только после проверки границ, permissions, opaque locks и отсутствия
пересечения активного API frame. Ошибки не создают объект или дескриптор.
Лимит 128 дескрипторов общий с событиями и DuplicateHandle; дубликаты
сохраняют identity. Последний CloseHandle **не завершает** приостановленный
поток. Last-error успешного создания отмечается неизвестным. Основание:
[CreateThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createthread),
[CreateRemoteThreadEx](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createremotethreadex).

Отдельный opt-in `--create-thread-interior` требует эту fixture и явный
reference kernel32.dll. Он принимает только точный структурный пролог из
5 инструкций/11 байт у non-forwarded CreateThread, без другого экспорта
на внутреннем адресе. Проверяются EIP, EBP=ESP+4, 36 байт в границах стека,
права чтения, копия thread-ID pointer и EAX=creation flags. Вывод thread ID
не может пересекать весь частичный frame, включая сохранённый EBP.

Только после проверки ESP/EBP временно приводятся к исходному API-вызову;
успешная модель возвращает их в состояние caller. При отказе CPU context
восстанавливается, фактическая остановка остаётся на внутреннем адресе.
Reference-код основным трассировщиком не исполняется. Это конкретный
структурный профиль, не общий alias всех внутренних API и не заявление
эквивалентности Windows. Hash helper и данные нормализации записываются
в отчёт. Исходник worker `0x1000f950` на диске сразу уходит в защитный
обработчик; роль worker в проверке лицензии пока не определена.

Перед новым реальным опытом прошёл **341 тест**: 15 focused-тестов interior
profile, сценарии suspended identity и Python/Rust integration parity.
Prefix и его READ/no-WRITE permissions перепроверяются при каждом входе,
не только при создании модели. Отдельные проверки меняют prefix/permissions
после инициализации и требуют отказа без изменения CPU/объектов.

### Локальное состояние событий без запуска worker

Opt-in `--event-state` добавляет SetEvent, ResetEvent и только немедленно
разрешимые WaitForSingleObject для живых модельных событий. Signaled event
даёт WAIT_OBJECT_0; auto-reset при этом сбрасывается, manual-reset сохраняет
сигнал. Nonsignaled event с timeout=0 даёт WAIT_TIMEOUT. Ненулевое ожидание
несигнального события остаётся остановкой, а не придуманным успехом или
истечением времени. Дубликаты дескриптора разделяют состояние события.
Основание: [SetEvent](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setevent),
[ResetEvent](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-resetevent),
[WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

Все созданные worker должны оставаться suspended и execution_started=false.
Нет пробуждения потоков, продвижения времени, ResumeThread или выполнения
нативных API. Неизвестные, закрытые и не-event handles отвергаются без
изменения состояния. Успешный вызов оставляет last-error неизвестным.
Снимки состояния до/после независимы от дальнейших изменений.

`model_handle_image_writes` хранит счётчик и последние 128 CPU DWORD stores
в исходные images, значение которых совпало с живым синтетическим handle.
Для каждого сохраняются адрес записи, инструкция, её индекс и identity.
Это кандидаты на ссылки, не доказательство назначения поля: равенство
может быть случайным. Стек и записи API в этот журнал не входят.

Перед опытом с этим профилем прошёл **361 тест**, включая Python/Rust
parity, отрицательные проверки ожиданий, общую identity дубликатов,
независимость снимков и ограничение размера журнала записей handles.

### Сигнал установлен; следующая граница — ResumeThread

`perv_event_state_4b_01.json`: **3 494 677 513 инструкций за 238,3938 с**.
SetEvent вернул модельный успех в `0x1000daec`; event:1 стал signaled,

CreateEventA → SetEvent → Wait(0) → Wait(0), с результатами 0 и WAIT_TIMEOUT
после auto-reset. Вместе с Rust-вариантом теперь проходят **363 теста**.
Уточнение pre-write semantics добавлено также в текст scope нового отчёта;
исторический JSON не переписан, его точные исходники сохранены в архиве.

### Подготовка отдельного эксперимента входа worker

`tools/pe_tls_metadata.py` проверяет PE32 x86 TLS только чтением файла:
VA/RVA, границы секций и raw backing, template/zero-fill, index output и
ограниченный NULL-terminated callback array. В отчёт попадают размеры,
адреса и SHA, но не байты template. Виртуальный template без raw backing
не объявляется повреждённым: metadata validity отделена от неизвестного
содержимого runtime. Проверка реального EXE подтвердила описанные выше
60 виртуальных байт; callbacks pointer NULL. Это не подготовка TLS.
Основание: [PE TLS directory](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#the-tls-section).

Индексы динамической TLS принадлежат процессу, значения — отдельным
потокам; значения creator нельзя автоматически наследовать worker.
В обычном запуске также существенны уведомления DLL_THREAD_ATTACH,
если они не отключены. Эти механизмы пока не реализованы; см.
[Thread Local Storage](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-local-storage)
и [DLL entry point](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-entry-point-function).

`--worker-entry-probe` — отдельный opt-in, **не реализация ResumeThread**.
Только на остановке ResumeThread с живым suspended model-thread он создаёт
независимый Unicorn с копией текущих bytes/permissions. Основной EIP,
API-стек, registry и suspend_count не меняются; main не продолжается.
Клон не сериализуется. Лимиты: 512 MiB, 8192 региона, копирование кусками
до 1 MiB. SHA каждого региона сохраняется без самих bytes.

Новые GDT/NT_TIB, стек и sentinel занимают отдельные непересекающиеся
адреса; конфликты отвергаются. Регистры и stdcall frame — явно синтетические.
Creator TIB не заменяется; обращение к нему останавливает опыт. Неизвестные
поля нового TIB, любые opaque lock accesses, все API/reference code,
переходы за пределы input images, системные/временные инструкции и ошибки
памяти также останавливают опыт. Никаких обработчиков startup API, TLS,
DllMain, scheduler, SEH dispatch или продолжения основного потока нет.

Начальный probe ограничен 100 000 инструкций / 2 секундами исполнения;
его небольшой stop-only observer — Python, тяжёлый parent остаётся Rust.
Первый достигнутый вызов означает зависимость **при выбранных fixture и
пропущенной инициализации**, не первую зависимость настоящего Windows-потока.
Даже возврат не доказывает правильный запуск worker или лицензию.

Перед реальным опытом прошли **395 тестов**: 17 TLS metadata, 13 отдельных
worker-probe tests и общая suite с Python/Rust parent parity. Интеграционный
тест собственного PE проверяет CreateThread → ResumeThread-stop → отдельный
возврат worker и неизменность parent-регистров/модели. Сравнение исключает
только измеренное время child setup/execution, не семантические поля.
Новый журнал handle stores также проверяет равенство DWORD в конце parent
(`final_value_matches`); это не доказательство завершения конкретной записи.

Независимый review выявил и закрыл три пробела child guard: RDRAND/RDSEED
и другие environment/privileged instructions, исполнение из opaque/creator
областей и аномальный размер CODE hook для invalid opcode. Размер теперь
проверяется как 1..15 до чтения; fetch guard проверяет весь interval;
Capstone privilege group и явный denylist останавливаются до исполнения.
Три новых regression tests довели suite до **398 PASS** (16 worker tests).
Эти изменения внесены, пока выполнялась parent-часть первого опыта: helper
импортируется и хешируется только после parent stop. Основной loader source
во время прогона не менялся; фактический helper SHA должен быть
`77080fad0a5f9b300594042a9a74989d2554f32a7bb9d6bc6db2ea7a4983b177`.

### Следующий контролируемый опыт: явные RDTSC sequences

Добавлен `--worker-rdtsc-sequence START:STEP:COUNT`: максимум три независимых
child-сценария из одного и того же parent state, 1..64 uint64 значения без
overflow. Базовый child без fixture по-прежнему останавливается на RDTSC.
В opt-in сценарии инструкция не исполняется: EDX:EAX получает очередное
явное значение, EIP продвигается, EFLAGS сохраняются. Исчерпание sequence
останавливает опыт. RDTSCP, random и privileged инструкции не разрешаются.
Это выбранные исследователем входные данные, не native timestamps и не
продвижение часов. Полные sequences и использованные значения журналируются.

Прошли **406 synthetic tests**, включая flags/high-low DWORD/exhaustion,
изолированные сценарии с одинаковыми clone hashes и Python/Rust parent parity.
Реальный опыт ЭРА с этой новой fixture **ещё не выполнен**; последнее
подтверждённое наблюдение остаётся RDTSC@`0x106928f4`, 843 инструкции.

### Ускорение классификации инструкций и отдельные бюджеты child

Классификация Capstone теперь кэшируется по **текущим точным байтам**
инструкции, а не по адресу. На каждом hook байты заново читаются из child;
проверки границ, API и запрещённых областей остаются перед lookup. Кэш
хранит только id/mnemonic/privilege, не операнды или адреса переходов;
максимум 4096 записей, затем сброс. В отчёт входят hits/misses/resets,
но не байты. `decode_cache=False` сохраняет эталонный режим без кэша.

Синтетические тесты сравнивают оба режима, включая самомодификацию
NOP→RDTSC по прежнему адресу: запрет RDTSC сохраняется. Проверены переполнение
кэша и строгий bool-параметр. На собственном цикле из 100 000 инструкций
получено 1,4364 с без кэша и 0,4337 с с кэшем (примерно ×3,31);
это единичный microbenchmark, не обещание такого ускорения всей трассы.

Добавлены явные `--worker-max-instructions` (1..1 000 000) и
`--worker-max-seconds` (>0..10); прежние defaults 100 000 / 2 с сохранены.
Нестандартные budgets требуют opt-in worker probe и не меняют parent budget.
Проверены границы, bool/NaN/Infinity, передача limits в child и неизменность
parent. Полный suite: **414 PASS**. Исходники заморожены перед новым опытом;
его результат будет зафиксирован отдельно, а не выведен из microbenchmark.

### Явная конечная fixture GetTickCount

`--worker-tick-count DWORD` можно повторить не более 16 раз. Это только
входные данные независимого child; parent clock/model state не меняется.
Без опции все API остаются остановками. Allowlist принимает только точное
имя `GetTickCount` в `kernel32.dll` (регистр имени модуля несущественен),
не GetTickCount64, другие DLL или API-set aliases. Полный диапазон uint32
разрешён, bool/float/overflow и длинные sequences отвергаются.

До любого изменения проверяются budget, наличие очередного значения,
четырёхбайтовое слово возврата внутри собственного synthetic stack и
исполняемый mapped return target внутри input image, вне references,
creator/opaque/fixture regions и известных API. Ошибка или исчерпание
останавливает child без частичного возврата. Успешный model event меняет
только EAX, ESP(+4), EIP; stack bytes/flags/прочие регистры сохраняются.
Это не выполнение системного кода и не измерение/продвижение часов.
Событие учитывается отдельно от instruction count. Значения и return targets
входят в отчёт. Suite — **423 PASS**, включая cache parity, atomic rejection
и неизменность parent при настоящем синтетическом import/call/return.

Для следующего опыта выбран один ранее продвинувшийся RDTSC-сценарий
`123456789:100000:1024` и одно tick-значение `123456`, совпадающее с явным
parent fixture. Это не доказательство согласованности двух native clocks;
никаких последующих API или лицензионных результатов модель не выдаёт.

Read-only проверка диска: `0x1000f950` и предполагаемый return `0x1000f9b2`
содержат token/переходы в protected dispatcher `0x106813a0`. В проверенном
диапазоне `[0x1000f950,0x1000fa60)` нет обычных FF15/FF25 ссылок на известные
IAT slots. Соседние stubs не устанавливают порядок выполнения; дисковое
линейное декодирование не заменяет live trace и не определяет роль worker.
