# Инициализация CRT: время, куча и граница TLS — 19.10.2026

Продолжение [исследования входа DLL](THREAD_INITIALIZATION_RESEARCH.md),
исходный коммит `dc231a3`. Полный DLL attach ещё не завершён. Рабочего
обхода ключа, эмуляции USB-устройства и запуска расчётного ядра нет.
Расчётный Rust CLI на этом этапе не изменялся.

## Проверенный результат

Эксперимент начинается с настоящего PE entry point `grdvkc32.dll`
`0x1031e641`, с аргументами `(0x10000000, DLL_PROCESS_ATTACH=1, NULL)`.
В отличие от отдельного вызова GrdPrepare, выполняется стартовый код CRT.

| Локальный отчёт | Инструкций CPU | Следующая внешняя граница |
| --- | ---: | --- |
| `grd_crt_startup_01.json` | 129 | `HeapCreate(0, 4096, 0)` |
| `grd_crt_startup_02.json` | 142 | `GetModuleHandleW` |
| `grd_crt_startup_03.json` | 173 | `TlsAlloc` |
| `grd_crt_startup_04.json` — повтор | 173 | `TlsAlloc` |

В первых двух прогонах использовались промежуточные версии инструментов;
их хеши сохранены в отчётах. Последние два используют одинаковые версии.

DLL сама записала модельный дескриптор кучи `0x74000000` по `0x1037f8e8`.
Это именно та переменная, которая оставалась нулевой в предыдущем
эксперименте с ошибкой `R6030`. Также изменены восемь байт состояния
защиты стека по `0x10364ac0`; хеши до/после сохранены без выгрузки байтов.
Ненулевое состояние кучи не означает завершения всей инициализации CRT.

Затем DLL запросила `GetModuleHandleW("KERNEL32.DLL")` и нашла через
реальную таблицу экспортов адреса `FlsAlloc`, `FlsGetValue`, `FlsSetValue`,
`FlsFree`. Поиск адресов не означает исполнения этих функций: код системных
DLL по-прежнему не исполняется. Следующим фактическим вызовом оказался
`TlsAlloc`, адрес возврата `0x10325b27`; модель остановилась до его выполнения.
Зафиксированы семь CPU-записей в `.data`, без CPU-записей в `.text`.

## Что моделируется и что остаётся неизвестным

Новая опция `--startup-model` явно включает синтетические условия:

- FILETIME `133485408000000000`, счётчик производительности `123456789`,
  PID `4096`, TID `4097`, GetTickCount `123456`. Это тестовые значения,
  не измерения Windows; течение времени не моделируется.
- `GetSystemTimeAsFileTime` записывает 8 байт и не получает выдуманный
  код успеха: функция VOID. `QueryPerformanceCounter` записывает 8 байт
  и возвращает модельный успех. Перед записью проверяется весь диапазон
  буфера, включая права памяти. [FILETIME API](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemtimeasfiletime),
  [QPC API](https://learn.microsoft.com/en-us/windows/win32/api/profileapi/nf-profileapi-queryperformancecounter).
- Кучи: ограниченная арена 16 МиБ по `0x50000000`, максимум 64 дескриптора,
  выравнивание блоков 16 байт. Поддержаны создание растущей кучи, выделение,
  перевыделение с сохранением префикса, размер, освобождение и уничтожение.
  Дескрипторы и принадлежность живых блоков проверяются; двойное освобождение
  останавливает эксперимент. Из этих операций в данной трассе достигнута
  только HeapCreate; остальные проверены синтетическими тестами.
- Кучи фиксированного максимального размера не поддержаны. Начальный размер
  проверяется на бюджет, но резервирование/commit страниц Windows не
  воспроизводится. Освобождённые блоки не переиспользуются и не исключаются
  из карты памяти; CPU-доступ после освобождения отдельно не отслеживается.
  HeapSize возвращает запрошенный размер, без моделирования служебных данных.
  Перевыделение всегда переносит блок; режим in-place не поддержан.
- Неинициализированные данные заполняются `A5`, запрошенные нулевые — нулями.
  Это явно выбранное модельное содержимое, не воспроизведение Windows heap.
  Превышение бюджета останавливает трассу, а не изображает реальный отказ
  HeapAlloc. [HeapCreate](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heapcreate),
  [HeapAlloc](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heapalloc),
  [HeapReAlloc](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heaprealloc).
- `GetModuleHandleW` ищет только явно отображённые модули, с ограниченным
  чтением UTF-16LE. NULL, пути и отсутствующие модули не заменяются
  успешным ответом или предположением об отсутствии DLL.
  [Контракт Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandlew).

Каждый поддержанный вызов сохраняет аргументы, результат и диапазоны записи.
Записи API-модели учитываются отдельно от записей CPU, поскольку Unicorn
не вызывает CPU write hook при записи из Python. Неизвестные системные,
лицензионные и аппаратные вызовы по-прежнему останавливают эксперимент.
ОС хоста, сеть, драйверы и USB не вызываются. TLS/FLS, last-error и
многопоточность ещё не реализованы; это не полноценная среда Windows.

## Воспроизведение и проверки

Использована DLL с SHA-256
`0eb1003dc43a6484f8bba7076a442fad8dad506bb80f6e9047d77c82f4c7ce30`.
Для последних двух прогонов нужен только один справочный 32-битный модуль
kernel32.dll с SHA-256
`d62d3ca4f677eb06ba81b1eba82f375c0c345f0e8f8097c92fc5e36e4d72294e`.
Другой файл Windows может иметь другие адреса/перенаправления экспортов.

```sh
python tools/loader_trace.py /path/to/grdvkc32.dll --dll-attach --thread-model --startup-model --module /path/to/x86/kernel32.dll --watch 0x10364ac0:8 --watch 0x1037f8e8:4 --max-instructions 10000000 --max-seconds 30 --report /new/path/startup.json
python -m unittest discover -s tools -p 'test_*.py' -v
```

В повторах совпали хеши четырёх инструментов, число инструкций, регистры,
внешний вызов и стек, контролируемая память, состояния потока, модулей
и startup-модели, счётчики CPU-записей. Это проверка указанных контрольных
точек, не доказательство эквивалентности Windows или всех путей исполнения.

Прошли 37 тестов Python на собственных искусственных данных и 59 тестов Rust,
включая локальный корпус методик. Хеши восьми исходных файлов ЭРА совпали
с прежним манифестом. CI запускает все `test_*.py`, оригинальные DLL для
этого не нужны. Публикация EXE и артефактов не включалась.

Собственный код, тесты, это описание и [манифест](research-checkpoint-2026-10-19-startup.json)
можно хранить публично. Полные отчёты остаются в локальном
`reverse_engineering/`; оригинальные бинарники и память не публикуются.
Следующий шаг — явная модель TLS/FLS со временем жизни и проверками индексов,
после чего продолжение entry. Вызов GrdPrepare в том же состоянии допустим
только после проверенного успешного attach, а не после ручного выставления
одного флага или дескриптора кучи.
