# Продолжение трассировки загрузчика — 19.10.2026

Рабочего обхода ключа нет. Этот этап расширяет лабораторную модель среды,
а не отключает лицензирование. Оригинальные файлы ЭРА не изменяются.
Предыдущая контрольная точка сохранена в [PROTECTION_RESEARCH.md](PROTECTION_RESEARCH.md)
и в коммите `02866c8`; её манифест описывает файлы на момент того коммита.

## Что изменилось в инструменте

По умолчанию `tools/loader_trace.py` по-прежнему останавливается при первом
импорте. Параметр `--module` включает отдельную ограниченную модель:

- Явно переданные x86 PE-модули отображаются по предпочтительным базовым
  адресам. Их таблицы экспортов читаются из реальных файлов, а не задаются
  списком придуманных адресов. Хеши фиксируются, неизменность проверяется.
- `GetModuleHandleA` разрешает только явно отображённый модуль по имени.
  `GetProcAddress` разрешает только существующий экспорт по имени или ordinal,
  включая цепочки forwarded exports в явно переданных модулях.
- `LoadLibraryA` поддерживает только случай уже отображённого модуля:
  возвращает его адрес и учитывает дополнительное приобретение ссылки.
  Поиск файлов, новая загрузка и вызов DllMain не моделируются; `FreeLibrary`
  остаётся точкой остановки. Начальный абсолютный счётчик ссылок неизвестен.
- Эти вызовы моделируются с возвратом адреса и очисткой аргументов
  x86 stdcall. Это допущение лабораторной среды, не наблюдение настоящего
  ответа Windows или успешной проверки лицензии.
- При неизвестном модуле, экспорте, неподдержанном параметре или другом API
  эксперимент останавливается. Нулевой результат вместо неизвестного
  ответа не подставляется; DLL автоматически не загружаются.
- Код системных DLL не исполняется даже в эмуляторе: вход в любой их адрес
  перехватывается до инструкции. Их отображённая память защищена от записи.

Семантика поиска сверена с документацией Microsoft:
[GetModuleHandleA](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandlea),
[GetProcAddress](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress),
[LoadLibraryA](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibrarya).
Реализовано только указанное подмножество контрактов, не полноценная Windows.

## Первые наблюдения

Отдельный вызов `GrdPrepare(-1)`:

| Локальный отчёт | Отображённые модули | Остановка | Инструкции |
| --- | --- | --- | ---: |
| `grd_resolver_trace_01.json` | kernel32 | запрос `User32.dll` | 44 253 852 |
| `grd_resolver_trace_02.json` | kernel32, user32 | запрос `Gdi32.dll` | 44 262 670 |
| `grd_resolver_trace_03.json` | десять системных DLL | `LoadLibraryA("Shell32.dll")` | 44 271 292 |
| `grd_resolver_trace_04.json` | те же десять DLL, модель уже загруженного Shell32 | чтение по адресу 0 | 45 893 948 |
| `grd_resolver_trace_05.json` | те же, с диагностикой адресации | чтение `fs:[edx]`, EDX=0 | 45 602 127 |
| `grd_resolver_trace_06.json` | повтор с неизменными инструментами | та же инструкция и состояние | 45 828 782 |

Обе остановки — на `GetModuleHandleA` для ещё не предоставленного модуля.
Ранее предоставленные имена успешно разрешены в рамках модели. В первом
прогоне 48 001 событие записи в `.grd0001`, во втором 48 062; записи в `.text`
до этих границ не наблюдались. Счётчики относятся к отдельным экспериментам.
Третий прогон выполнен до добавления модели `LoadLibraryA`: библиотека
shell32 уже отображалась, но вызов ещё не поддерживался. Эти ранние отчёты
описывают последовательные версии инструмента (SHA-256 указаны в отчётах),
а не три прогона одной неизменной реализации.

В прогонах 04/05 совпали четыре вызова, конечные регистры и 48 123 события
записи только в `.grd0001`, но не счётчик инструкций. Причина расхождения
счётчиков не установлена; временные инструкции CPU не фиксируются.
Нельзя утверждать детерминированность полной трассы.
Повтор 06 с теми же SHA-256 обоих инструментов подтвердил результат 05:
совпали конечные регистры, адрес/тип ошибки, описание инструкции,
журнал четырёх вызовов, хеши модулей и счётчик записей. Число инструкций
снова отличается; это не объясняется одной лишь сменой версии инструмента.

## Новая граница: сегментная адресация FS

В прогоне 05 инструмент декодировал инструкцию непосредственно из текущей
эмулируемой памяти, а не из зашифрованных байтов на диске. На `0x1069a9ad`
наблюдается `mov` с четырёхбайтным операндом через сегмент `fs`, базовый
регистр `edx` и нулевое смещение. EDX=0; чтение останавливается по линейному
адресу 0. После перечисленных четырёх вызовов новых внешних API до остановки
не наблюдалось, `GetProcAddress` на этом пути ещё не вызывался.

В x86 Windows FS используется для обращения к TEB; FS:0 связан с цепочкой
обработчиков исключений. Это описано Microsoft в материалах
[о TEB](https://devblogs.microsoft.com/oldnewthing/20190203-00/?p=101028)
и [предупреждении C4733](https://learn.microsoft.com/en-us/cpp/error-messages/compiler-warnings/compiler-warning-level-1-c4733).
Следовательно, наблюдение согласуется с отсутствующей средой потока/SEH
в нашей модели. Оно **не доказывает** отказ лицензии, NULL-ошибку оригинала,
намеренную антиотладочную ловушку или невозможность дальнейшего анализа.
Назначение окружающего обработчика ещё не восстановлено.

Следующий этап — корректная настройка сегмента FS, состояния потока и
обработки исключений с отдельными синтетическими тестами. Простая подстановка
нулей в отсутствующую память не даёт достоверного продолжения.

## Ограничения и воспроизведение

Нет PEB/TEB, TLS, запуска DllMain, CRT, обработки Windows-исключений,
состояния last-error, API-set mapping и переноса модулей на другие базы.
Коллизия адресов приводит к отказу, а не к незаметной порче образа.
Возврат адресов не доказывает, что модуль был бы корректно инициализирован
в настоящем процессе. Поведение зависит от конкретной версии системных DLL.
Никакого USB-ключа, драйвера, сервера лицензирования или их ответов здесь нет.

Пример первого эксперимента (пути к собственным локальным файлам):

```sh
python tools/loader_trace.py /path/to/grdvkc32.dll --export GrdPrepare --argument=-1 --module /path/to/x86/kernel32.dll --max-instructions 100000000 --max-seconds 180 --report /new/path/grd-resolver.json
```

Отчёт должен сохраняться в существующий каталог под новым именем.
Для прогонов 04/05/06 дополнительно переданы `--module` для user32.dll,
gdi32.dll, advapi32.dll, ntdll.dll, comdlg32.dll, shell32.dll, ole32.dll,
comctl32.dll, shlwapi.dll из локального каталога x86 SysWOW64. Их SHA-256
и предпочтительные адреса записаны в отчётах. Другие версии DLL могут
иметь пересекающиеся базы: инструмент явно отклонит такую конфигурацию.
В публичный репозиторий не включаются системные DLL, файлы поставки ЭРА,
дампы памяти и байты стороннего кода. Полные отчёты остаются локально.

Синтетические тесты: `python -m unittest discover -s tools -p 'test_loader_trace.py' -v`.
Проверены разрешение имён/ordinal, stdcall-стек, отсутствующие модули,
циклические forwarders, коллизии адресов, защита памяти, остановка до
исполнения экспортов и произвольных адресов системных DLL. Тестам не нужны
ни Windows, ни оригинальная ЭРА.

Локальная проверка: 14 синтетических тестов трассировщика и 59 тестов Rust
с `--features recovered-tests` прошли. Восемь файлов поставки из прежнего
манифеста повторно сверены по SHA-256: изменений нет.

Хеши текущих исходников, локальных отчётов и модулей зафиксированы в
[манифесте этапа](research-checkpoint-2026-10-19-resolver.json).
Полные локальные отчёты не публикуются; манифест не заменяет их содержимого.
